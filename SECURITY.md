# Security Policy

This document is containd's public vulnerability disclosure policy (VDP) and coordinated disclosure process.

Machine-readable discovery:

- `/.well-known/security.txt` when served from the appliance UI
- [`ui/public/.well-known/security.txt`](ui/public/.well-known/security.txt) in the repository

The `.well-known` segment is the literal standards-defined URL path for these files. This repository stores them under `ui/public/.well-known/...` so shipped UI builds serve the same `/.well-known/...` paths at runtime.

## Supported Versions

| Version | Supported |
| ------- | --------- |
| `0.1.x` | Yes |

## Reporting a Vulnerability

Do not open a public GitHub issue for security vulnerabilities.

Primary contact:

- Email: **tony@defendics.com**

Please include:

1. A clear description of the issue and why you believe it is security-relevant.
2. Affected versions, deployment mode, and whether the finding requires non-default configuration.
3. Reproduction steps, proof of concept, logs, screenshots, or packet captures as appropriate.
4. Any suggested mitigation or fix if you have one.

## Safe Harbor

The containd project supports good-faith security research carried out in line with this policy.

If you:

- avoid privacy violations, data destruction, and service interruption;
- avoid accessing accounts or data that do not belong to you;
- make a good-faith effort to avoid unnecessary harm;
- report the issue promptly and give the project a reasonable opportunity to investigate and mitigate it;
- do not publicly disclose exploit details before coordinated disclosure is agreed;

then the project will not recommend or pursue legal action solely for that research activity.

This safe-harbor statement applies to research intended to improve the security of containd and does not excuse unlawful behavior, destructive testing, or actions that exceed the bounds above.

## Coordinated Disclosure Expectations

What to expect from the project:

- acknowledgment of receipt within `48 hours`
- initial triage within `5 business days`
- follow-up on severity, scope, and likely remediation path after triage
- coordination before public disclosure for confirmed vulnerabilities

Project goals for disclosure:

- fix or mitigate confirmed vulnerabilities as quickly as practical
- publish release notes and advisories clearly enough for operators to understand impact
- credit the reporter unless the reporter prefers to remain anonymous

The exact publication timeline depends on severity, exploitability, release readiness, and whether users need mitigation guidance before a full fix ships.

## Scope

The following are in scope:

- the `containd` Go binary and packaged runtime behavior
- the containd Docker images and release artifacts
- the management API, web UI, SSH console, and CLI
- authentication, authorization, session management, and secrets handling
- config lifecycle, backup/export handling, and redaction behavior
- network enforcement, nftables programming, NAT, routing, conntrack visibility, and related policy application
- logging, audit, event export, and security-relevant telemetry generated by containd

## Out of Scope

The following are generally out of scope unless containd's integration is the root cause:

- vulnerabilities in third-party software with independent security processes, such as Envoy, Nginx, Unbound, OpenVPN, or ClamAV
- denial of service against disposable lab deployments running with intentionally weak defaults
- findings that depend entirely on a user leaving the documented bootstrap credential unchanged after first login
- social engineering, phishing, physical attacks, or compromise of systems not controlled by this project

If a finding involves an upstream dependency, reporting it to the upstream maintainer is still appropriate. Please also notify containd so the project can track and ship an updated dependency.

## Testing Guidelines

Permitted testing should be limited to systems, data, and accounts you own or are explicitly authorized to test.

Please do not:

- access, modify, or delete data that is not yours
- intentionally degrade availability for shared or public systems
- use high-volume automated scanning against systems you do not control
- pivot from a containd finding into unrelated infrastructure or third-party services

For classroom and local-lab deployments, reproductions against your own containerized environment are preferred.

## Advisories and CVEs

When the project publishes a security fix, the preferred public artifacts are:

- a GitHub release with clear release notes
- a GitHub Security Advisory when appropriate
- a CVE record when appropriate and available
- a CSAF document when the issue warrants a machine-readable advisory record

Project goals for advisories and CVE publication:

- describe the affected versions and fixed versions clearly
- include mitigation guidance when a fix is not immediately available
- include root-cause information such as CWE when practical
- keep changelog, advisory text, and release notes aligned

Machine-readable publication points:

- `/.well-known/security.txt`
- `/.well-known/csaf/provider-metadata.json`
- [`security/csaf/advisories/`](security/csaf/advisories/) in the repository for published CSAF documents

Published advisory: [containd-2026-001](security/csaf/advisories/containd-2026-001.json).
See the [CSAF index](security/csaf/README.md) for discovery and publication details.

The presence of CVEs is not treated as a failure by itself. The project cares more about root-cause reduction, clarity, and remediation quality than raw counts.

## Hardening Guidance

- Set a unique, non-empty `CONTAIND_JWT_SECRET` for every deployment.
- Rotate the bootstrap password immediately through the web UI or management API.
- Keep `CONTAIND_LAB_MODE=0`; lab mode pins predictable credentials and prevents
  password rotation. Use it only in disposable, isolated labs.
- Prefer HTTPS, replace the generated self-signed certificate for trusted remote
  access, and restrict management ports to authorized operators.
- Enable TOTP MFA for administrative accounts. SSH password login then asks for
  the code; see the authentication limits below.
- Prefer SSH keys and disable SSH password authentication when feasible.
- Review policy exceptions and apply supported security releases promptly.

Canonical operational guidance: [Secure by Design](docs/mkdocs/secure-by-design.md),
[Threat Model](docs/mkdocs/threat-model.md) and [Update Policy](docs/mkdocs/update-policy.md).

## Authentication Limits

Fresh local-account installs use the predictable bootstrap credential
`containd` / `containd`. Outside lab mode, web/API and SSH enforce the required
password-change flow, and both support optional TOTP MFA for local accounts:

- SSH requires an admin account. The bootstrap admin must change its password at
  SSH login before the CLI, menu or shell opens.
- SSH password login of an MFA account asks for a TOTP code. SSH public-key login
  does not: the key is treated as the possession factor, so a key alone signs in.
- An account whose MFA enrollment grace period has ended cannot log in over SSH
  until it enrolls through the web UI.
- A password or MFA change ends the account's other sessions and SSH connections.
- A TOTP code is accepted once per account, on web/API and SSH.
- The SSH menu and setup wizard ask for the current password before changing it.
- Refused SSH logins are audited. SSH password, key and TOTP failures share one
  rate limit per client address and account, so many addresses or account
  names are not limited together.
- TOTP codes and the current password asked before a password or MFA change
  are also limited per account, from every client address, web and SSH
  together. After 5 wrong codes, or 10 wrong current passwords, without a
  success, that check alone is locked for 15 minutes: it is refused (web/API
  `429` with `Retry-After`) before the guess is checked, and the first refusal
  of each lock is audited. Password login is not locked, so someone without
  the password cannot lock an account out; reaching the TOTP lock takes the
  right password. Resetting the password or MFA lifts the locks.

Lab mode (`CONTAIND_LAB_MODE=1`) skips SSH password-change and MFA assurance,
the per-account factor limits, and TOTP replay protection. It pins the bootstrap
credential. SSH still requires an admin account and a valid password or authorized
key; SSH password attempts remain rate-limited.
An authenticated SSH PTY can reach the appliance's Linux shell, not
just a restricted configuration CLI. The supplied appliance runs as root inside
its container; treat SSH access as privileged appliance access. Keep it
unreachable from untrusted networks.

## Engine API Trust Boundary

The engine API is privileged and separate from management authentication/MFA.
Numeric loopback listeners retain credential-free plaintext HTTP. Every other
listener (including wildcard and `localhost`) requires TLS 1.3 mutual
authentication derived from one dedicated `CONTAIND_ENGINE_SECRET`, even in lab
mode or without enforcement. Management refuses remote plaintext and redirects.

Combined mode (`containd all`) defaults to `127.0.0.1:8081`. Split engine mode
has no default: set `CONTAIND_ENGINE_ADDR` to an interface-held management-network
address and management's URL to `https://` with the same secret on both peers.
Shared-namespace reserved deployments require loopback instead. Keep the network
private; firewall admission and Docker isolation remain defense in depth.

Every holder of the engine secret can act as either peer; exported client keys
can call every engine route. Rotate by changing both peers and restarting both,
then replace scraper credentials. Namespace-local peers and host/root-controlled
forwarding are trusted for loopback; exposing it through a proxy is unsupported.
Host networking makes loopback host-wide. See the
[transport and rotation guide](docs/mkdocs/docker-compose.md#engine-secret-and-rotation).
